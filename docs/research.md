# My Long Diary - 구현을 위한 연구 및 분석 문서 (Research)

이 문서는 `rfp.md`에 명시된 요구사항을 바탕으로 "My Long Diary" 데스크톱 어플리케이션을 구현하기 위한 관련 기술, 배경 지식, 그리고 최적의 구현 방안을 조사 및 분석한 결과입니다.

---

## 1. 요구사항 핵심 분석 (Core Analysis)

*   **감성적이고 정제된 경험 (Emotional & Refined)**: 복잡한 기능(글꼴 서식 지정 등)을 배제하고 오직 텍스트 기록에만 집중할 수 있는 깔끔한 UI/UX가 필요합니다.
*   **완벽한 프라이버시 (Privacy & Encryption)**: 일기라는 특성상 데이터 보호가 필수이며, 중간 수준의 암호화가 도입되어야 합니다. 자동 저장 기능이 함께 연계되어 데이터 유실을 방지해야 합니다.
*   **높은 마이그레이션 가능성 (High Migration)**: 이 앱의 가장 중요한 차별점입니다. 앱 서비스가 종료되거나 OS 환경이 바뀌더라도 사용자의 일기는 영구적으로 보존되고 접근 가능해야 합니다. 하루 단위의 개별 파일(1일 1파일) 형식으로 저장하여 언제든 백업/복원 및 타 앱으로의 이동이 쉬워야 합니다.

---

## 2. 기술 스택 제안 (Tech Stack Proposal)

**"Windows, Mac, Linux 크로스 플랫폼"** 요구사항을 충족하기 위해 데스크톱 애플리케이션 프레임워크가 필요합니다. 

### 후보군 비교: Tauri vs Electron
*   **Electron**: 풍부한 생태계와 안정성을 자랑하지만 앱 용량이 크고 메모리 점유율이 높습니다.
*   **Tauri**: 데스크톱의 네이티브 웹뷰를 사용하여 **앱 번들 크기가 매우 작고(몇 MB 수준), 메모리 사용량이 적습니다.** 백엔드로 Rust를 사용하여 파일 시스템 접근 및 암호화 처리에 있어 매우 빠르고 안전합니다.

**✅ 결론: Tauri + React(또는 Vue) + Tailwind CSS 스택을 추천합니다.**
일기 앱 특성상 항상 백그라운드에 켜두거나 빠른 실행이 중요하므로, 리소스 사용량이 적은 **Tauri**가 가장 적합합니다. 프론트엔드는 React 환경을 통해 부드러운 상태 전환과 렌더링에 집중합니다.

## 3. 핵심 기능 구현 방안 (Implementation Details)

### 3.1. 파일 시스템 및 데이터 스키마
*   **파일 구조**: 일기는 로컬 디렉토리에 개별 파일로 저장됩니다.
    *   형식: `YYYY-MM-DD.md` (예: `2026-03-03.md`)
    *   내용은 마크다운 문법을 유지하되, 암호화 설정 시 파일 내용은 암호문으로 덮어씌워집니다. (이 경우 확장자를 `.enc` 로 두거나 `.md` 내부 텍스트를 암호화 블록으로 감싸는 형태 제안)
*   **이어 쓰기 (Append)**: 해당 날짜의 일기 탭을 열면 기존 텍스트를 불러오고, 이어서 작성할 수 있도록 렌더링합니다.

### 3.2. 영구 보존을 고려한 암호화 전략 (Encryption)
*   **목적**: 앱이 구동되지 않는 미래에도 사용자가 비밀번호만 알면 복호화할 수 있어야 합니다. (종속성 탈피)
*   **알고리즘 제안**: 널리 쓰이는 표준 방식인 **AES-256-GCM** 또는 **AES-256-CBC** 알고리즘 사용.
*   **구현 방법**:
    1.  사용자가 설정한 암호를 기반으로 **PBKDF2**나 **Argon2** 알고리즘을 사용해 고정 길이의 '암호화 키(Key)' 생성.
    2.  일기 저장 시 임의의 초기화 벡터(IV)와 Salt를 생성하여 내용을 암호화.
    3.  파일의 앞부분(Header)에 `[Salt]:[IV]:[암호화된 데이터]` 평문 형태로 함께 저장.
*   **독립적 복호화 보장**: 추후 사용자가 앱 없이도 일기를 읽을 수 있도록, 범용적인 Python 복호화 스크립트를 공식 Github이나 사용자 PC의 일기 폴더 루트에 `README.md` 혹은 `decrypt_tool.py` 형태로 상시 배포해 두는 방안을 제안합니다.

### 3.3. 자동 저장 메커니즘 (Auto-save)
*   사용자의 타이핑마다 암호화 및 파일 쓰기를 수행하면 I/O 병목이 발생할 수 있습니다.
*   **Debouncing 처리**: 사용자가 타이핑을 멈춘 후 N초(예: 2초)가 지나면 백그라운드에서 현재 에디터 상태를 암호화하여 즉시 덮어쓰기(`fs.writeFile`)를 수행합니다.
*   내결함성(Fault Tolerance)을 위해 임시 폴더에 먼저 작성(`tmp`)한 후 기존 파일을 원자적으로 교체(Atomic Rename)하는 방식을 통해 저장 도중 전원이 꺼져도 파일이 손상되지 않게 방지합니다.

### 3.4. 기존 일기 임포트 (Import)
*   디렉토리 선택 다이얼로그 연동 (Tauri API 또는 Electron dialog).
*   폴더 내의 `.txt` 및 `.md` 파일을 일괄 순회 분석.
*   정규식 파싱을 통해 파일명에서 개별 날짜(YYYY-MM-DD)를 추출하고, 추출이 어려운 경우 시스템의 '마지막 수정일(mtime)' 또는 '생성일(ctime)'을 기준으로 하여 앱의 표준 포맷으로 컨버팅 후 지정 경로에 이동시킵니다.

### 3.5. UI/UX 및 디자인 세팅
*   **레이아웃 구성**:
    *   **좌측 사이드바**: 연/월별 아코디언 메뉴 혹은 무한 스크롤 리스트 뷰.
    *   **메인 에디터**: 제목, 날짜, 에디터 본문. 부가적인 툴바는 없애거나 최소화(호버 시 희미하게 나타나는 구조).
*   **몰입 모드 (Distraction-Free)**: 단축키 혹은 버튼 클릭 시 좌측 사이드바가 슬라이드 아웃되며 에디터가 화면 중앙에 배치되는 모드 구성.
*   **테마 및 폰트**:
    *   CSS Variable 기반의 테마 시스템 (그레이톤 라이트모드 / 다크모드).
    *   시스템 기본 폰트 스택(San Francisco, Segoe UI, Noto Sans 등)을 `font-family` 맨 앞에 두어 OS 기본 타이포그래피의 유려함을 해치지 않게 조율합니다.
    *   설정 페이지에서 폰트 지정 및 글꼴 크기 변경 시 즉각적으로 전역(:root CSS 변수)에 반영되게 처리.

## 4. 후속 개발 권장 단계 (Next Steps)

1.  **초기 프로젝트 스캐폴딩**: Tauri(Rust) + React 템플릿 프로젝트 생성.
2.  **프로토타이핑**: 좌측 사이드바 및 우측 그레이톤/다크 모드가 적용된 심플한 Markdown 에디터 UI/UX 구축.
3.  **파일 입출력 연동 (Local IO API)**: 일기 경로 지정 및 날짜별 1일 1파일 생성 및 읽기 로직 개발 (에디터 내 텍스트와 실제 OS 파일 동기화).
4.  **암호화 모듈 구현**: 파일 저장 및 읽기 중간에 암호화/복호화 레이어 적용.
5.  **기타 유틸리티 추가**: 임포트 기능, 사용자 설정(폰트 등) 저장 로직 구현.
